# 串口工具技术栈调查文档

> 版本：v0.3 ｜ 调查日期：2026-08-29
> 状态：**Windows-only 复评版**（基于实际网络调查重写）
> 历史版本：v0.1 初版调查 → v0.2 跨平台 Go B/S 方案（**已作废**，macOS 需求取消后主要动因消失）

## 0. 需求变更与本次复评动机

| 项 | v0.2（作废） | v0.3（本次） |
| --- | --- | --- |
| 目标平台 | Windows + macOS | **仅 Windows 10/11** |
| 架构动因 | 绕开 Mac 签名公证 → B/S 浏览器形态 | 动因消失，重新评估 |
| 分发 | Go 单二进制 zip | **免安装优先**（自包含单 exe） |
| 其余需求 | 不变：UART/RS232/RS485 + I2C + CAN 模块化（UART 先行）、协议级解析、可选波形 | 同左 |

**复评原则**：不带沉没成本（现有 Go 骨架约 2 天工作量，可归档），以网络调查的当前生态事实为唯一依据。

## 1. 调查发现（2026-08 实查）

### 1.1 UI 框架现状（Windows 桌面）

| 框架 | 2026 年状态 | 来源 |
| --- | --- | --- |
| **WPF** | 社区共识"依然正确"：稳定、功能完整、生态最大；Windows-only 场景首选 | [Reddit r/csharp](https://www.reddit.com/r/csharp/comments/1v8w1wq/windows_ui/)、[softwarerecs 讨论](https://softwarerecs.stackexchange.com/questions/90037/) |
| WinUI 3 | 稳定性抱怨多、开发节奏慢、Windows App SDK 打包对免安装不友好 | 同上 + [CTCO 对比](https://www.ctco.blog/posts/winui-vs-wpf-2026-practical-comparison/) |
| Avalonia | 编译绑定、活跃开发，但优势在跨平台——本项目已不需要 | [Avalonia 官方博客](https://avaloniaui.net/blog/wpf-modernization-in-2026) |
| 经验法则 | "Windows-only → WPF；要 Win11 外观 → WinUI3；要跨平台 → Avalonia" | [实践总结](https://note.com/loyal_koala8607/n/n828b47cccf6b) |

**结论**：Windows-only + 免安装场景下，WPF 仍是 2026 年的正解；WinUI 3 被排除（稳定性 + 打包）。

### 1.2 串口库（.NET 生态）

| 库 | 评估 | 来源 |
| --- | --- | --- |
| `System.IO.Ports`（NuGet v10.x） | 够用，但有已知坑：`DataReceived` 事件行为不可预测、高吞吐丢数据 | [Sparx 深度分析](https://sparxeng.com/blog/software/must-use-net-system-io-ports-serialport)、[MS Learn](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport?view=net-11.0-pp) |
| **`SerialPortStream`（RJCP）** | 专为解决上述问题而生：独立原生实现、自有缓冲管理，高性能串口应用首选 | [GitHub](https://github.com/jcurl/RJCP.DLL.SerialPortStream) |

**结论**：V1 起直接用 `SerialPortStream`，避开 `System.IO.Ports` 的历史坑。

### 1.3 适配器 SDK 官方支持（本次调查的决定性发现）

I2C/CAN 适配器厂商 SDK 的**官方语言支持**直接影响 V2/V3 成本：

| 适配器 | 官方 .NET 支持 | 证据 | 其他语言 |
| --- | --- | --- | --- |
| FTDI FT232H（I2C，MPSSE） | ✅ **官方 NuGet `FTDI.FTD2XX_NET`** + 官方 AN411《C# MPSSE I2C Master 示例》 | [NuGet](https://www.nuget.org/packages/FTDI.FTD2XX_NET)、[FTDI C# 示例页](https://ftdichip.com/software-examples/code-examples/csharp-examples/)、[AN411](https://ftdichip.com/software-examples/mpsse-projects/libmpsse-i2c-examples/) | Go 需 cgo+mingw；Rust 第三方 |
| PEAK PCAN（CAN） | ✅ **官方 NuGet `Peak.PCANBasic.NET` v5.1.0**，支持 CAN CC/FD/XL | [NuGet](https://www.nuget.org/packages/Peak.PCANBasic.NET/)、[官方文档](https://www.peak-system.com/documentation/API/PCAN-Basic.Net/) | 同上 |
| CANable（CAN，slcan） | 走虚拟串口文本协议，任何语言零 SDK | [CANable 官方](https://canable.io/getting-started.html) | 全平台 |
| 辅助生态 | .NET IoT 库（System.Device.Gpio）含 FT232H I2C 托管支持；MPSSELight 第三方轻量库 | [MS Learn](https://learn.microsoft.com/en-us/dotnet/iot/usb)、[GitHub](https://github.com/zhelnio/MPSSELight) | — |

**结论**：**C# 是唯一获得 I2C/CAN 适配器厂商官方 SDK 支持的候选语言**。V2/V3 阶段其他语言都要自啃 FFI（Go 的 cgo 在 Windows 还需额外安装 mingw 工具链）。

### 1.4 波形/图表库

| 库 | 能力 | 来源 |
| --- | --- | --- |
| **ScottPlot 5（WPF 控件）** | `SignalPlot` 官方确认**百万点实时交互渲染**（min/max 预处理）；`DataStreamer` 滚动实时数据；WPF 控件开箱即用 | [官方 Cookbook](https://scottplot.net/cookbook/5/ScottPlotQuickstart/SignalPerformance/)、[实测 200 万点](https://www.linkedin.com/pulse/plotting-c-part-4-scottplot-amir-doosti-lerdf) |

**结论**：ScottPlot 5 的 SignalPlot 直接满足"数据级时序图 + 未来信号曲线"全部需求，且是所有候选方案中图表能力最强、无需自研的。

### 1.5 免安装（自包含单文件）发布

| 方案 | 免安装形态 | 体积 | 注意 |
| --- | --- | --- | --- |
| .NET 10 WPF | `dotnet publish -r win-x64 --self-contained -p:PublishSingleFile=true -p:EnableCompressionInSingleFile=true` → 单 exe 双击即用，目标机零依赖 | ~60-80MB | **WPF 不支持 trimming**（裁剪后启动失败，[已知问题](https://developercommunity.visualstudio.com/content/problem/1292518/)），体积无法再压 |
| Wails v2 | 单 exe | 10-20MB | 依赖 WebView2 运行时（Win10/11 普遍预装，[官方文档](https://wails.io/docs/guides/windows)） |
| Tauri 2 | 单 exe | ~5MB | 同上 + Rust |

**结论**：C# 方案体积是最大弱点（60-80MB），但换来零运行时依赖（连 WebView2 都不需要）；作为工程调试工具可接受（同类 VS Code 100MB+）。

## 3. 结论与推荐

### 3.1 推荐方案：C# / .NET 10 + WPF

```
┌──────────────────────────────────────────────┐
│ WPF UI 层（MVVM）                             │
│  · 收发控制台  · 帧解析视图  · 波形面板(ScottPlot) │
│  · AvalonDock 停靠布局（IDE 式多面板）           │
├──────────────────────────────────────────────┤
│ Core 解析引擎（纯 C# 类库，xUnit 单测）          │
│  · framing 帧状态机 · checksum 校验库           │
│  · templates 协议模板(JSON) · DBC解析(V3)       │
├──────────────────────────────────────────────┤
│ 硬件后端层（IBusBackend 接口，插拔式）           │
│  · SerialBackend    ← V1（SerialPortStream）   │
│  · I2cBackend       ← V2（FTDI.FTD2XX_NET）    │
│  · CanBackend       ← V3（Peak.PCANBasic.NET   │
│     或 CANable slcan 复用串口）                  │
└──────────────────────────────────────────────┘
分发：dotnet publish 自包含单 exe（~70MB，零依赖，双击即用）
```

### 3.2 决定性理由（按权重排序）

1. **适配器 SDK 官方支持**（§1.3）：FTDI、PEAK 均有官方 .NET NuGet——V2 I2C / V3 CAN 阶段零阻力，这是其他所有语言的硬差距
2. **ScottPlot 波形**（§1.4）：百万点实时渲染，波形需求一步到位
3. **AvalonDock**（§1.7）：免费实现 IDE 级专业布局
4. **社区共识**（§1.1）：Windows-only → WPF 2026 年依然成立
5. **SerialPortStream**（§1.2）：绕开 System.IO.Ports 历史坑

**接受的代价**：体积 60-80MB（WPF 无法 trim）；现有 Go 骨架归档（~2 天工作量，帧解析引擎尚未动工、设计平移无损）。

### 3.3 次选：Wails (Go)

若不愿放弃 Go 投入：保 95% 代码换原生窗口，10-20MB。代价是 V2/V3 需啃 cgo+mingw，波形靠 web 图表库，停靠布局要自研。**仅当"C# 学习成本"被判定为不可接受时选此路**。

### 3.4 被否方案

| 方案 | 否决理由 |
| --- | --- |
| Go + 浏览器 B/S（v0.2 方案） | 存在动因（Mac 签名）消失；浏览器标签页形态非桌面工具主流 |
| WinUI 3 | 稳定性 + Windows App SDK 打包与免安装冲突 |
| Avalonia | 优势在跨平台，本项目不需要 |
| Electron | 100MB+ 且无官方适配器 SDK 优势 |
| Tauri 2 | Rust 成本 + crate 覆盖不全 |
| Qt C++ | 开发效率低，Windows-only 下无独占优势 |

## 4. 风险与对策

| 风险 | 概率 | 对策 |
| --- | --- | --- |
| WPF 单 exe 体积大（60-80MB） | 确定 | 接受（工程工具可接受）；`EnableCompressionInSingleFile` 压缩 |
| 未签名 exe 触发 SmartScreen 蓝警告 | 确定 | 小范围分发先接受"仍要运行"；正式分发购 OV 证书（与语言选型无关） |
| XAML/MVVM 学习曲线 | 中 | 用 CommunityToolkit.MVVM 降低样板代码；骨架期即建立模式 |
| WPF 无法 trimming | 确定 | 不启用 PublishTrimmed（已知会崩，§1.5 来源） |
